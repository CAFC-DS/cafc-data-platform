# ADR 0001 — APP_COMPAT is a strangler-fig bridge, not the destination

**Status:** Accepted · **Date:** 2026-06-01

## Context

The recruitment platform (FastAPI + React, separate repo) is **live** — ~51 users
across 5 roles — and today reads its data from `RECRUITMENT_TEST.PUBLIC.*`. The
canonical data platform (this repo) is standing up a clean `CORE` layer (IMPECT-
derived players/squads/KPIs via dbt, plus app-owned operational tables) and an
`APP_COMPAT` schema of views that re-present `CORE` data in the legacy table
shape the app currently expects.

Recurring question: is it right to keep "rebuilding in the legacy way so the app
can still read it," or should we do a clean/complete rebuild of the schema and
cut the app over in one move?

Two distinct data families are involved, and they answer differently:

- **IMPECT-derived analytical data** (players, squads, competitions, seasons,
  KPIs/scores) — generated by this repo's dbt from `IMPECT_RAW`.
- **App-owned transactional data** (scout reports, attribute scores, report
  views, lists, recommendations, notes, stage history, assignments, users) —
  **written by the app**, currently in `RECRUITMENT_TEST.PUBLIC`. dbt does not
  and must not "rebuild" these; they are user-generated, not derived.

## Decision

Use the **strangler-fig** pattern via `APP_COMPAT` views. Do **not** big-bang
rebuild. Specifically:

1. `APP_COMPAT.*` views present canonical `CORE` data in the legacy shape and
   **emit dual IDs** (legacy + canonical `CAFC_*`) plus `DATA_SOURCE`, so the
   app's existing dual-ID filters keep matching during transition.
2. The app cuts over **feature-by-feature**, lowest blast-radius first
   (read-only search/profile/analytics → notes → scout reports + lists →
   recommendations → admin). Rollback for any feature = flip
   `PLATFORM_DB_SCHEMA` back to `RECRUITMENT_TEST.PUBLIC` (plan §3).
3. `APP_COMPAT` views are **explicitly temporary scaffolding**. The end state is
   the app reading `CORE` **natively** in canonical shape, after which the
   compat views and `RECRUITMENT_TEST.PUBLIC` are retired (plan §3's 30-day
   quiet-period retirement).
4. App-owned transactional tables are never dbt-rebuilt. They migrate homes
   (`RECRUITMENT_TEST.PUBLIC` → `CORE`) and gain a canonical-player-ID join via
   the identity layer; the compat view over them is a thin reshape + identity
   join.

## Why not a complete (big-bang) rebuild

The app is live. A clean rebuild would mean redesigning the schema, migrating
~8k scout reports + ~44k attribute scores, rewriting the app's data layer, and
coordinating a flag day against real users — one giant rollback if it goes
wrong. The strangler approach reaches the same clean end state incrementally,
each step reversible.

## Discipline required (or the bridge becomes the architecture)

The known failure mode of compat layers is that "temporary" becomes permanent.
We already have evidence: `APP_COMPAT.SCOUT_REPORTS` still reads
`FROM CORE.SCOUT_REPORTS_TEST` — a hand-built, un-versioned view pointing at a
`_TEST` table the §1.3 cleanup was meant to rename away. So:

- **Compat views must be dbt-managed** (versioned, tested, reproducible). The
  4 scout-report `APP_COMPAT` views are currently hand-built and not in the
  repo — bringing them under dbt (and fixing the `SCOUT_REPORTS_TEST` repoint)
  is required, not optional.
- **They must emit dual IDs** so per-feature cutover and rollback work.
- **They must be time-boxed** with a written end-state: app on native `CORE`,
  compat views dropped.

## Consequences

- Sequencing: canonical identity work (`core_*_id_resolutions`, the §2.6
  matcher) is the prerequisite — compat views can only emit canonical IDs once
  identities resolve. So identity → app_compat dbt models → Part 3 cutover.
- Two layers coexist during migration (accepted, temporary).
- A follow-up task list: (1) fix `SCOUT_REPORTS_TEST` → `CORE.SCOUT_REPORTS`
  repoint, (2) formalize the 4 scout `APP_COMPAT` views as dbt models with dual
  IDs + tests, (3) drive per-feature cutover, (4) retire `RECRUITMENT_TEST.PUBLIC`.
